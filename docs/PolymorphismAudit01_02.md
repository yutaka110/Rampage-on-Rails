# 01_02 ポリモーフィズム

敵の移動、編隊、敵弾、コースイベント、武器の発射方式に継承によるポリモーフィズムを適用した。資料の評価条件に沿って、基底型の仮想関数と仮想デストラクタ、派生型の `override`、基底参照を介した本番呼び出しを確認した。実装の選択には既存の種類IDを使い、敵や武器の状態は引き続き各ランタイムが所有する。各実装は実行中に変化する状態を持たず、敵や弾を生成するたびにオブジェクトを確保せずに共有できる。

## 採用した設計

| 適用箇所 | 共通契約と呼び出し元 | 採用理由 |
| --- | --- | --- |
| 敵の基礎移動 | `EnemyMovementPattern::Evaluate` を `AdvanceEnemyBehaviorMovement` が呼ぶ。[実装](../application/course/EnemyBehaviorSystem.cpp) | 側面展開、迎撃、ボスなどで式が変わる。スナイパーと支援機は同じ余弦の実装を周波数だけ変えて共有する。実機の敵更新と照準予測は同じ基礎移動を評価する。 |
| 編隊の相対配置 | `EnemyFormationLayout::Slot` を `EnemyFormationSystem::UpdateActors` が呼ぶ。[実装](../application/course/EnemyFormationSystem.cpp) | V字・縦列・円陣などは、同じ隊列番号に対して異なる空間配置を計算する。左右の斜列は符号違いの同じ方式として扱う。 |
| 敵弾 | `EnemyProjectileFlight::AimAtLaunch` と `Advance` を発射計画・軌道予測・通常更新が呼ぶ。[実装](../application/course/EnemyProjectileSystem.cpp) | 直進と予測照準は同じ飛翔、弧状弾は重力補正、追尾弾は旋回を使う。予告側からはライブ照準を渡さず、実弾側では元の旋回順序を維持する。 |
| コースイベント | `CourseEventDispatcher::EventHandler::Execute` を `Dispatch` が呼ぶ。[実装](../application/course/CourseEventDispatcher.cpp) | 編隊生成、障害物、ボス、演出キューは処理が独立している。ボス生成後のキュー、欠損したウェーブの代替キュー、入力順を維持する。 |
| 武器の発射方式 | `WeaponFirePolicy::Activate` と `Schedule` を `WeaponFireSystem::Update` が呼ぶ。[実装](../application/course/WeaponFireSystem.cpp) | 押下・保持・連射・解放で発火判定と発射枠が異なる。チャージ解放とロックオン斉射は解放判定を共有し、弾数や熱量は武器システムで一貫して更新する。 |

## 点検した候補と設計の根拠

対象はルート、`application`、`engine`、`lib`、`tools` の追跡対象 C++ 1,232ファイル。型・種類・状態による条件分岐、既存の仮想インターフェース、テンプレートと `std::variant` の使用箇所を調べた。

| 候補 | 設計を選んだ理由 |
| --- | --- |
| 編隊の進入・退場、敵の標準設定、攻撃予告の強さ、速度ゾーン、スコア係数 | 方式の違いは係数または設定値として表せる。進入・退場は `TransitOffsetScale` の表と共通の補間式で扱う。編隊の離脱優先順位や地形制約は所有するシステムで適用する。 |
| コースの生成条件、敵の攻撃予約、安全条件、ドッジ、セッション、ポストプロセスの進行 | いずれも有限個の段階と共有タイマーを持つ状態機械。遷移条件と副作用を同じ更新処理で追えるため、予告・発射・中断の順序とチェックポイントに保存する状態が明確になる。 |
| 敵の個別演出、Fang弾の収束、起動直後の特殊経路 | コースや個別演出の条件を、共通の移動・軌道に適用する補正として扱う。通常の敵種別と演出上の特例を独立に組み合わせられる。 |
| 被弾対象の種類、命中防御、描画・音声キュー、エディターの変更コマンド | レイキャスト結果、通知、コマンドは決まった種類と値を持つ。所有側で解釈することで、被弾の重複排除、キューの消費順、エディターのトランザクション境界を維持できる。 |
| 地形・デブリ、選択用の境界、カメラ設定 | 配置データとレール座標を純粋な計算に渡す。シード付きの生成とエディターの選択境界は用途が異なり、プレビューと実行時で具体的な幾何条件を検証できる。 |
| アニメーション条件、Behavior Tree、EQS、Visual Script、ブラシの操作値 | 保存形式や命令セットで定義されたタグをデータとして評価する。保存・読込・移行とランタイムで同じ形式を扱える。 |
| VFXコンポーネント、警告図形、描画パスの組み立て | VFX の既知の格納形式は型付きデータと `std::variant`、警告図形の合成はコンパイル時に決まる `template<class Emit>` を利用する。API や GPU が要求する形式・ハンドルは値として渡す。 |
| アプリのシーン切替、エディターの文書・ツール・Undo/Redo、シーン部品生成 | すでに基底型と具体実装を使っている。代表例は `IAppSceneState`、`IEditorDocumentProvider`、`IEditorUndoCommand`、`IEditorSceneRuntimeComponentFactory`。 |
| プラットフォームメッセージ、リソース種別、列挙値の文字列化、失敗理由 | Windows・D3D12 や既存フォーマットの固定の値を変換する境界。ここでは分岐が対応関係を直接示す。 |

## 検証

- Release x64 のビルドは警告0件、エラー0件。標準スクリプトの環境検査には既存のツールバージョンとライセンスハッシュの差があるため、インストール済みの MSBuild で `CG4.sln` をビルドした。
- 最終版の `GE3.exe --editor-core-regression` で既存321件を実行し、全件通過した。01_01 の基準ログとテスト名・実行順を照合した。
- 既存のテスト内に、弧状弾にだけ重力がかかること、欠損ウェーブの代替キューとイベント順を維持することを追加した。
- 通常起動の実機操作でタイトルから出撃し、ゲームオーバー後に「リトライ」を選択した。`FINAL PURSUIT` のチェックポイントへ復帰し、車体とコースの位置がともに 1450.09 に戻ったことをログで確認した。通常戦闘と被弾表示の再開も画面で確認した。
- 同じシナリオを変更前後の Release 版で再生し、敵の予告と発射、編隊6機の画面外への離脱、ブレーキからブーストへの移行を確認した。ブースト中の採取フレームでは速度が両方とも 41.23、カメラの画角は 1.02419 rad と 1.02407 rad だった。
- 戦闘区間 2140–2440 で、敵が活動中の30フレーム間隔の計測値を比較した。画面提示の待ち時間を除く CPU 所要時間の中央値は 14.955 ms から 13.438 ms だった。各5サンプルのため、当該区間の参考値とする。
