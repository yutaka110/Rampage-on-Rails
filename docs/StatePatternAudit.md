# State Pattern 課題

敵やセッションの状態に応じた処理を状態クラスへ移し、各クラスが遷移の条件と行き先を決めるようにした。状態ID・タイマー・照準や攻撃の識別子は従来のランタイムが所有する。状態クラスのインスタンスには実行中に変わるデータを持たせず、同じ実装を共有する。これにより、状態の変更時にオブジェクトを確保せず、チェックポイントや照準予測では従来の値型をそのまま複製できる。

## 本番での適用箇所

| 対象 | 状態が決めること | 維持した契約 |
| --- | --- | --- |
| [敵の行動](../application/course/EnemyBehaviorSystem.cpp) | 進入・位置調整・照準・発射要求・回避・再配置。照準状態が時間と距離を判定し、攻撃要求を作る。 | 予告のカウントダウンは攻撃枠・表示通知・射撃環境がそろってから進む。発射確定と中断は既存の通知で受け付ける。 |
| [敵の戦闘状態](../application/course/EnemyCombatSystem.cpp) | 出現から交戦、発射後の回復、被弾からの復帰、撃破からの退場。 | 発生済みの被弾・発射を取り込んでから現在状態を更新し、その後に新しい状態の射撃可否などを反映する。照準予測でも同じ状態更新を使う。 |
| [セッション](../application/course/GameSessionSystem.cpp) | イントロ終了、プレイ中の勝敗、勝敗演出からリザルトへの移行。 | ポーズ復帰、同フレームで勝敗条件が成立した場合の優先度、タイマーとイベントの発行順を維持する。 |
| [レールシューター内のシーン](../application/AppRunLoop.cpp) | タイトルは準備完了を判定してプレイへ進む。敗北状態はゲームオーバーの更新とリトライ・タイトルへの選択を処理する。 | 出撃への引き継ぎは従来と同じフレーム。敗北判定と復元結果はセッションが所有する。既存の `IAppSceneState` はアプリ最上位のシーンを扱う。 |
| [基本チュートリアル](../application/course/RailBasicTutorial.h) | 現在のガイドが次の表示を選ぶ。ロックオン状態が短い見失いを許容し、その後はルートの優先規則に従う。 | 表示中のカードと独立して操作の成功を記録する。リトライで学習済みの操作を引き継ぐ。 |
| [ボス撃破後の進行](../application/course/RailPostBossSequence.h) | 撤退演出、展望、橋への進入、警告、後方戦、脱出への遷移。 | 前段の評価、敵の生成と追跡、戦闘、脱出の順を維持する。戦闘から脱出に移ったフレームに脱出処理が動く。 |
| [橋の脱出](../application/course/RailBridgeEscape.h) | 警告・旋回・照準、クランプへの命中、助走・飛行・着地。 | 発射操作の時点では橋を開かず、対象への命中と破壊を確認してから進む。離陸と着地を同じ距離更新でまたいだ場合も、着地を一度だけ通知する。 |

### 資料の4条件を示す代表例

1. `AimingState` が敵の照準状態を表す。
2. `BehaviorState::Update` を `AimingState` が `override` する。
3. `EnemyBehaviorSystem::UpdateActors` が、敵の状態IDに対応する基底参照経由で呼ぶ。
4. `AimingState` が照準時間と攻撃可能な距離を見て `BeginAttackIntent` を要求する。その操作が状態を発射要求へ進め、攻撃IDを発行する。

## 点検した候補の設計理由

ルートと `application`、`engine`、`lib`、`tools` の追跡対象C++ 1,232ファイルを、状態型の宣言、状態代入、状態別の条件分岐、既存の仮想呼び出しを手掛かりに点検した。

| 候補 | 採用した方式と理由 |
| --- | --- |
| 攻撃枠の予約、任務・ウェーブの配信 | `EnemyAttackCoordinator` は複数機に対して予約上限と優先順位を一度に処理する。攻撃枠は共有資源として調停し、個体の照準と発射要求は敵AIの状態で進める。ウェーブ条件はコースデータで定義する。 |
| 車体の回避、姿勢、ブースト、武器の熱・装填 | 移動・熱・入力・リロードには同時に成立する条件がある。単発の回避などは同じ入力、時計、補間値から結果を求め、独立した能力の組み合わせとして表す。発射操作の方式は01_02の発射ポリシーを使用する。 |
| 編隊の進入・退場、地形とカメラの連続演出 | 定義データの有効範囲、進捗、係数を使って座標を計算する。既存の調整値でプレビューと実機の両方を検証できる。敵の個別行動遷移は敵AIが扱う。 |
| ゲートと尾根のコース区間 | 距離、視認時間、撃破済みの合図によるコース固有の進行条件を、区間単位の進行処理に置く。敵の数やカメラの引き継ぎは区間全体の条件に従う。 |
| ゲームオーバーの車体、タイトル演出、ポストプロセス | 分解、煙、カメラ、画面効果を一つの時刻で評価する。複数演出の重なりを時間で指定できる。シーンとしての出撃と敗北は状態クラスで処理する。 |
| アニメーション、Behavior Tree、Visual Script、エディターの操作データ | 条件や命令をエディターで調整して保存し、ランタイムが同じデータを評価する。追加の行動や演出をデータ側から設定できる。 |
| エディターとエンジンの処理段階 | ウィンドウ、描画、保存、ストリーミングなどの既存の状態IDは、処理結果と進行状況の通知にも使う。画面・ツール・文書の切替で既に使われる仮想インターフェースと合わせて点検した。 |

## 検証

- Release x64 は警告0件、エラー0件。前回と同様、インストール済みの MSBuild で `CG4.sln` をビルドした。
- Release 版の `GE3.exe --editor-core-regression` で既存の321件がすべて通過した。01_02 の基準ログと、テスト名および実行順が一致した。
- 既存テストに、イントロが終了したフレームではプレイ時間をまだ加算しないことと、一度の距離更新で離陸・着地をまたいでも着地通知が一度に限られることを加えた。
- 通常起動の実機操作でタイトルから出撃し、ゲームオーバー画面でリトライを選んだ。チェックポイント `FINAL PURSUIT` のコースと車体の距離が、保存時と同じ 1450.51 に戻り、2回目の戦闘が再開した。
- 同条件で通常コースを再生し、予告から発射まで、編隊6機の離脱、ブレーキからブーストの順を前後のビルドで確認した。後方戦への進入は、後方に2機が出現しカメラの旋回が完了した状態を映像とログで確認した。
- 橋の脱出は、比較専用のコースコピーで中ボスの対象パーツを60 HP、追撃機を120 HPにそろえてテストした。両ビルドともクランプへの実際のロックオン命中を経て、警告から着地完了まで同じ8段階を通過した。ボス撃破位置を基準にした脱出完了距離は 824.86 と 824.85 だった。
- 敵が活動する区間 2140–2440 を、前後のビルドを交互に切り替えて各3回計測した。画面提示の待ち時間を除く CPU 所要時間の中央値は 15.046 ms と 15.026 ms、ゲーム更新の中央値は 6.727 ms と 7.010 ms だった。いずれも各15サンプルの当該区間の参考値とする。
